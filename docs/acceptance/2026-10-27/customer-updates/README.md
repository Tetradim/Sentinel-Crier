# Windows 0.3.0 update acceptance

Accepted runtime source: `ff01c87f1f08bbe9ed77d34940878780bf99350c`. Exact workflow results and integrity evidence are recorded in [source evidence](source-evidence.json), [installer lifecycle acceptance](installer-acceptance.json) and the [live public update probe](public-probe.json).

The final Windows workflow passed **1,126 Python tests**, with one optional SDK skip, built/smoke-tested the packaged application, passed installer installation/upgrade/downgrade-refusal/uninstall checks, signed the public update manifest and published [Windows 0.3.0](https://github.com/Tetradim/Sentinel-Crier/releases/tag/v0.3.0). Installer lifecycle upgrades use an acceptance-only next patch version with the same program payload; this does not validate arbitrary future database migrations or physical customer installation.

A live unauthenticated public probe used the actual update client and bundled public trust policy. It discovered the release for a 0.2.0 source, verified the Ed25519 signature, downloaded the public installer, rechecked its signed size/SHA256 and confirmed that a 0.3.0 client reports current. The owner PC did not execute that installer. Discovery initially exposed GitHub's HTTP 415 rejection of the wrong metadata Accept header; the regression was observed failing, repaired and verified against the real endpoint before publication.

Synthetic tests exercise real Ed25519 signatures, duplicate JSON/schema rejection, version/profile/protocol eligibility, bounded body/header/TLS/connect/DNS operations, cancellation, symlink/junction/target races, private staging, WAL snapshots, opaque protected credentials, backup tampering, exclusive restore, profile format refusal, failed/canceled shutdown and signing producer/consumer compatibility. Native Windows helper tests verify file/directory guards and hashes in verification-only mode without executing an installer.

Review repaired file/directory replacement races, sticky install intent after shutdown failure, equal-version source-range rejection and resolver deadline gaps. The updater pins HTTPX 0.28.1/httpcore 1.0.9 because its narrow network backend deadline adapter relies on their implementation boundary; dependency changes must retain those regression tests. At most two daemon DNS resolutions can remain outstanding after cancellation; callers and normal app shutdown do not wait indefinitely for the OS resolver.

Only the public release key is bundled. The dedicated signing key/password are repository Actions secrets, with a local Windows-user DPAPI backup outside source and customer profiles. No broker credentials, real order placement, Discord messages or Supabase deployment were involved. Publication itself was a deliberate signed-release action after verification.

Physical/customer upgrade testing, Microsoft publisher certificate/reputation, Apple enrollment/distribution, Android APK auto-update delivery and real broker acceptance remain outside this Windows update acceptance. The current release adds no database format migration. Review the [customer/publisher guide](../../../customer-updates.md) before future releases or recovery; restoring local data cannot reverse broker activity.
